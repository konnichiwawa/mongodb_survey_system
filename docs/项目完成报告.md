# 基于 MongoDB 的问卷系统开发——项目完成报告

## 一、项目目标

本项目旨在开发一个基于 MongoDB 的简化在线问卷系统，实现用户注册与登录、问卷创建与管理、题目配置、问卷发布与分享、在线答题以及问卷结果统计等功能。

系统支持单选题、多选题、文本题和数值题，并提供题目答案校验及条件跳转逻辑。通过本项目，进一步理解 MongoDB 的数据建模方法、后端 API 的设计方式，以及问卷业务中的数据关联和业务规则实现。

## 二、系统设计

### 2.1 系统整体结构

系统采用前后端分层的设计思路，以 Python 作为后端开发语言，使用 Flask 提供 HTTP API 服务，并使用 MongoDB 存储系统数据。

系统主要包括以下部分：

1. **用户认证模块：** 负责用户注册、登录、退出登录及当前登录状态查询。
2. **问卷管理模块：** 负责创建问卷、查询本人创建的问卷、发布问卷、关闭问卷及设置截止时间。
3. **题目管理模块：** 负责创建、查询、修改和删除问卷题目。
4. **答题模块：** 根据问卷分享码获取已发布问卷，并接收和校验用户提交的答案。
5. **统计模块：** 根据答卷数据统计答题数量、选项分布、文本答案及数值题的统计结果。

### 2.2 主要业务流程

用户首先注册并登录系统，然后创建问卷并添加题目。问卷至少包含一道题目后才能发布。发布成功后，系统生成可供访问的分享路径。填写者登录后可以访问已发布且未超过截止时间的问卷，填写答案并提交。系统保存答卷数据，问卷创建者可以查询相应的统计结果。

### 2.3 API 设计

系统采用 REST 风格的 API 组织业务接口，主要包括用户认证、问卷管理、题目管理、答卷提交和统计查询等接口。具体请求路径、请求方法、参数和返回结果见《项目文档》中的 API 说明。

### 2.4 后端处理架构

系统后端基于 Flask 提供 API 接口，并通过不同的路由模块组织用户认证、问卷管理、题目管理、答卷提交和统计查询等功能。MongoDB 负责保存用户、问卷、题目和答卷数据，后端负责处理请求参数、身份认证、业务规则和数据校验。

一次业务请求主要经过以下步骤：

1. **接收请求并检查输入。** 后端读取客户端提交的数据，检查必要字段是否存在、数据类型是否正确，以及输入内容是否满足基本要求。
2. **验证用户身份与操作权限。** 对需要登录的接口，后端根据当前会话识别用户；对于问卷管理和统计操作，还需要检查当前用户是否有权操作对应问卷。
3. **执行业务规则。** 根据操作类型检查问卷状态、题目归属、发布条件、答案校验规则或条件跳转规则，避免仅凭客户端传入的数据直接执行操作。
4. **访问 MongoDB 并处理结果。** 在通过相应检查后，后端查询或更新对应集合，将有效的业务数据保存到数据库，或者读取已有数据进行统计。
5. **返回接口响应。** 后端向客户端返回处理结果和必要的数据；对于无效输入、权限不足或不符合当前业务状态的请求，返回相应的错误信息。

这种处理方式将接口接收、业务判断和数据持久化的职责区分开来。数据库负责保存数据，后端负责保证业务流程按照规定执行，从而减少无效数据写入和越权操作的风险。

## 三、MongoDB 数据库设计

### 3.1 设计背景与总体目标

本系统是一套基于 MongoDB 的问卷系统，主要完成用户注册与登录、问卷创建、题目管理、问卷发布、答卷提交、条件跳转和结果统计等功能。数据库不仅需要保存这些业务数据，还需要为后端的权限校验、答案验证、问卷状态管理和统计查询提供可靠的数据基础。

在设计数据库时，我没有直接按照页面功能逐一建立数据表，而是先考虑不同数据对象之间的关系，以及它们在系统中的生命周期。

例如，用户可以创建多份问卷；一份问卷可以包含多道题目；一份问卷发布后可以收到多份答卷；每份答卷又包含多个题目的回答。这些对象虽然存在关联，但它们的创建、修改和查询方式并不相同。如果将它们全部存放在一个集合中，文档结构会越来越复杂，不同业务操作也容易相互影响；如果将所有内容都拆成很细的集合，又可能增加不必要的查询和数据组织成本。

因此，本系统采用以业务实体为基础的集合划分方式，将用户、问卷、题目和答卷分别存储，再根据数据之间的关系决定是否使用嵌入式文档。对于需要独立管理的数据，使用独立集合；对于与所属对象关系紧密、通常需要一起读取的数据，则优先考虑嵌入式结构。

本次数据库设计主要遵循以下原则：

1. **职责清晰。** 每个集合对应相对明确的业务实体，减少不同业务数据之间的耦合。
2. **数据结构与业务特点相匹配。** 根据题目类型的差异，灵活保存选项、校验条件和跳转规则。
3. **控制数据冗余。** 尽量避免同一份需要独立维护的数据在多个位置重复存储，降低修改时出现不一致的风险。
4. **数据与执行逻辑分离。** 将问卷、题目中可变化的业务配置保存到数据库，由后端统一读取、校验和执行。
5. **兼顾数据完整性与查询效率。** 利用后端校验、访问权限检查和索引共同维护数据的正确性。
6. **考虑数据规模的增长。** 避免将可能持续增长的题目列表和答卷列表无限嵌入同一个问卷文档。

这些原则并不是彼此独立的。例如，将题目拆分到独立集合可以避免问卷文档不断膨胀，但也会增加读取问卷完整内容时的查询工作。因此，设计时需要结合实际访问场景进行权衡，而不能只追求集合数量少或者文档结构简单。

### 3.2 整体数据模型与集合划分

本系统主要使用 `users`、`surveys`、`questions` 和 `responses` 四个集合，分别保存用户、问卷、题目和答卷数据。

| 集合 | 主要职责 | 设计理由 |
|---|---|---|
| `users` | 保存用户账号及认证所需的信息 | 用户具有独立的注册、登录和身份识别流程 |
| `surveys` | 保存问卷基本信息、创建者、状态、分享码和截止时间等 | 问卷具有独立的创建、发布、关闭和访问控制流程 |
| `questions` | 保存题目内容、题型、所属问卷、排序、选项、校验配置和跳转规则等 | 题目需要独立管理，而且不同题型的配置存在差异 |
| `responses` | 保存答卷所属问卷、答题者标识、答案列表和提交时间等 | 每次提交都应形成独立记录，以便后续查询和统计 |

这里的集合划分并不是简单地将所有字段平均拆开，而是根据各类数据的业务职责和变化方式进行划分。

#### 3.2.1 用户集合 `users`

用户集合用于保存账号信息，为登录认证和问卷管理权限判断提供基础。

用户身份需要被其他业务对象引用。例如，创建问卷时，后端需要记录问卷的创建者；查询个人问卷时，需要根据当前登录用户筛选其有权查看的问卷。

因此，用户数据应当独立保存，而不应将用户名和密码信息复制到每份问卷或每份答卷中。否则，一旦用户信息发生变化，就可能出现多处数据不一致的问题，也会增加敏感信息暴露的风险。

在账号安全方面，数据库应保存密码哈希，而不是直接保存用户输入的明文密码。登录时，后端通过密码验证机制检查用户提供的密码是否与已保存的哈希匹配。这样可以将账号认证与问卷业务逻辑分开，使用户身份验证成为其他受保护接口可以复用的基础能力。

#### 3.2.2 问卷集合 `surveys`

问卷集合保存一份问卷自身的基本信息，例如标题、说明、创建者标识、发布状态、分享码、截止时间及相关时间信息。

我将问卷基本信息与题目内容分开保存，主要是因为问卷和题目虽然存在一对多关系，但承担着不同的业务职责。

问卷负责描述整份调查，包括问卷的基本信息、归属、可访问状态和有效期限；题目负责描述具体需要回答的问题，包括题型、选项、验证条件和跳转规则。两者的修改频率和管理操作也有所不同。

例如，修改问卷标题不应该要求重新保存全部题目；调整某一道题的选项，也不应该导致整份问卷的基本信息被整体重写。因此，将问卷基本信息放入 `surveys`，将题目放入 `questions`，有利于减少无关字段的读取与更新。

此外，问卷状态也是后端业务流程中的重要依据。问卷创建后处于草稿状态，满足发布条件后才允许发布；发布后可以关闭，答卷接口也需要根据状态和截止时间判断问卷是否仍然允许提交。

将这些信息统一保存在问卷文档中，可以让后端在执行发布、关闭和提交等操作时，明确地依据问卷当前状态作出判断。

#### 3.2.3 题目集合 `questions`

题目集合保存问卷中的具体问题。每道题通过问卷标识与所属问卷建立逻辑关联，并通过题目顺序确定其在问卷中的位置。

本系统支持单选题、多选题、文本题和数值题。不同题型需要保存的内容并不完全相同：

- 单选题和多选题需要选项列表。
- 文本题需要文本长度等校验条件。
- 数值题需要数值范围、整数限制等配置。
- 题目还可以具有必答设置和条件跳转规则。

如果强制所有题目采用完全相同的固定字段结构，部分字段就会对某些题型失去意义。例如，文本题通常不需要选项列表，而数值题的校验条件也与选择题不同。

因此，本系统使用题目类型字段区分题目种类，并通过选项、校验配置和跳转规则等字段保存与题目有关的具体设置。后端根据题目类型解释这些配置，而不是为每道题建立完全独立的数据结构。

这种设计使题目内容和题目行为配置可以统一管理，同时保留不同题型之间的差异。

#### 3.2.4 答卷集合 `responses`

答卷集合用于保存用户提交的调查结果。每次成功提交都形成一份独立答卷，其中包含所属问卷、答题者标识、答案列表和提交时间等信息。

我没有将全部答卷直接嵌入问卷文档，主要考虑到答卷数量具有持续增长的可能性。随着问卷被更多人填写，如果每次提交都需要更新问卷文档中的一个大型数组，文档会不断膨胀，也会让问卷基本信息的读取和更新承担不必要的负担。

将答卷单独保存后，新增答卷主要影响 `responses` 集合，不需要把所有历史答卷重新组织到问卷文档中。同时，统计功能可以根据问卷标识查询对应答卷，再对答案进行汇总。

这种设计也让答卷的保存与问卷基本信息的维护形成相对清晰的边界：问卷描述调查本身，答卷描述某次实际提交的结果。

### 3.3 数据之间的关系与关联方式

虽然 MongoDB 使用文档模型，但这并不意味着不同业务实体之间不需要明确的关系。本系统仍然需要维护用户、问卷、题目和答卷之间的逻辑关联。

主要关系如下：

- 一个用户可以创建多份问卷。
- 一份问卷可以包含多道题目。
- 一份问卷可以对应多份答卷。
- 一份答卷可以包含多个题目的回答。

这些关系主要通过文档中的关联标识表达，而不是依靠数据库自动维护传统关系数据库中的外键约束。

例如，题目文档通过所属问卷的标识确定归属，答卷文档也通过问卷标识确定自己属于哪份问卷。后端在查询或修改数据时，需要根据这些关联标识检查数据归属，而不能仅仅因为客户端提供了一个合法格式的 ID，就认为客户端有权操作对应对象。

这里有一个重要的后端设计原则：**标识用于定位数据，权限检查用于判断是否允许操作。两者不能混为一谈。**

例如，用户请求修改某道题时，后端除了检查题目是否存在，还需要确认该题属于当前用户拥有的问卷，并检查问卷是否处于允许编辑的状态。提交答卷时，也需要确认答案所对应的题目确实属于当前问卷。

因此，数据库的关联设计需要与后端的权限校验和业务校验配合，才能形成完整的数据管理机制。

从架构上看，MongoDB 保存实体数据和关联标识，后端负责按照业务规则解释这些关系并执行操作。这样的方式能够保持数据组织相对灵活，但也意味着开发者需要主动设计好关联校验，不能完全依赖数据库自身完成所有完整性约束。

### 3.4 为什么采用独立集合与嵌入式文档相结合的设计

MongoDB 支持将数据存储为独立文档，也支持在文档中嵌入子文档和数组。本系统没有采用单一的存储方式，而是根据数据的生命周期、增长特点和读取需求进行选择。

#### 3.4.1 为什么不把所有数据都放在一个集合中

如果将用户、问卷、题目和答卷全部放在一个集合中，虽然可以减少集合数量，但文档可能需要同时承担多种职责。

例如，问卷文档可能同时包含用户信息、全部题目和全部答卷。随着问卷数量和提交次数增加，文档结构会变得复杂，许多只需要读取问卷标题的操作也可能面对大量无关数据。

此外，不同业务操作可能需要修改同一个大型文档，增加更新逻辑的复杂程度。用户、题目和答卷的生命周期也不同，将它们全部放在一起会使数据组织与实际业务职责不够匹配。

因此，本系统不采用把全部业务数据集中在一个文档或集合中的方式，而是优先保证业务实体之间的职责边界清晰。

#### 3.4.2 为什么不把所有内容都拆成独立集合

另一种方式是将选项、校验规则、跳转规则乃至每个答案都拆分到不同集合中。这样的设计可以进一步细分数据，但并不一定更合理。

例如，题目的选项通常属于题目本身，编辑题目时往往需要同时读取选项；校验条件和跳转规则也主要服务于对应题目。如果将这些内容分别存储，读取一道完整题目时就需要额外查询多个集合，更新时也需要处理更多关联操作。

因此，我认为集合划分不应该单纯追求细致，而应该看数据是否具有独立管理的必要性，以及拆分后是否真正带来了好处。

对于具有独立生命周期、可能大量增长的数据，例如用户、问卷、题目和答卷，使用独立集合更合适；对于与主体联系紧密、通常一起读取和更新的配置数据，嵌入式文档更自然。

#### 3.4.3 本系统具体采用的嵌入方式

本系统主要采用以下嵌入式结构：

- 题目的选项通过数组保存在对应题目文档中。
- 题目的校验条件保存在 `validation` 配置中。
- 题目的条件跳转规则保存在 `jump_rules` 配置中。
- 一次答卷中的多个答案保存在该答卷文档的 `answers` 数组中。

采用这些结构的原因是，它们与所属题目或答卷具有较强的业务关联，通常需要在处理对应对象时一起读取。

例如，处理一道多选题时，后端需要读取题目类型、选项和多选数量限制。如果这些信息都在同一个题目文档中，后端就可以围绕一个明确的数据对象进行校验，减少额外的数据查询。

同样，一份答卷中的多个答案共同构成一次提交的结果。将它们放在同一答卷文档中，有利于把一次提交组织成一个相对完整的数据单元。

当然，嵌入式文档也并非越多越好。如果某个数组可能无限增长，或者其中的元素需要频繁独立查询和修改，就需要重新评估是否应该拆分。对于本系统而言，选项和规则通常与题目一同维护，单份答卷中的答案也对应一次提交，因此采用嵌入方式具有合理性。

### 3.5 数据冗余控制与一致性考虑

在数据库设计中，数据冗余并不一定意味着所有重复字段都应该被禁止。关键是区分必要的关联信息和不必要的重复业务数据。

本系统尽量避免在多个文档中重复保存同一份需要独立维护的完整数据。

例如，题目统一保存在 `questions` 集合中，而不是再将所有题目完整复制到问卷文档中。这样，当题目标题、选项或配置发生变化时，后端只需要维护对应的题目记录，不必同步更新多个副本。

与此同时，题目和答卷保留所属问卷的标识，是为了确定数据归属和支持按问卷查询。这类关联标识服务于业务查询，并不等同于重复保存整份问卷数据。

为了维持数据一致性，后端还需要在具体业务操作中进行检查：

1. 创建或修改题目时，检查问卷是否存在、当前用户是否有管理权限，以及问卷是否允许编辑。
2. 发布问卷时，检查问卷状态、题目数量和截止时间等条件。
3. 提交答卷时，检查问卷是否仍然开放、题目是否属于该问卷，以及答案是否满足题目配置的要求。
4. 查询统计结果时，根据问卷标识筛选答卷，避免将其他问卷的数据混入统计结果。

这些检查说明，数据一致性并不只依赖集合结构，还依赖后端执行操作时的约束。

MongoDB 不会因为题目文档中保存了问卷 ID，就自动保证对应问卷一定存在；也不会仅凭答案中包含一个题目 ID，就自动判断这个题目是否属于当前问卷。因此，这些关联规则需要由后端主动验证。

另外，嵌入式结构有利于将紧密相关的数据放在一起，但并不能自动解决所有并发更新问题。对于更复杂的多文档操作，如果未来需要保证多个集合之间的强一致更新，可以根据具体业务需求进一步评估事务或其他一致性机制。本项目目前主要通过明确的业务流程和后端校验管理这些关系，不将尚未实现的事务机制作为现有系统的能力。

### 3.6 为什么不采用关系数据库结构

从功能上看，关系数据库完全可以实现本问卷系统。用户、问卷、题目和答卷之间存在明确的关联关系，使用关系数据库的表、主键、外键及关联查询同样能够完成相关业务。

因此，选择 MongoDB 并不是因为关系数据库无法解决这些问题，而是因为本项目的题目配置存在一定的结构差异，MongoDB 的文档模型与这些配置的组织方式比较契合。

#### 3.6.1 不同题型具有不同的数据结构

本系统支持单选题、多选题、文本题和数值题。不同题型需要的字段并不相同。

例如，选择题需要保存选项数组；文本题需要处理文本长度限制；数值题需要处理数值范围和整数要求；不同题目还可能设置不同的跳转规则。

在关系数据库中，可以通过题目主表、选项表、校验配置表和跳转规则表等结构保存这些数据，也可以根据具体情况采用 JSON 字段。这样的方案是可行的，但需要进一步决定不同题型的配置如何组织、如何关联，以及如何进行查询和维护。

对于当前项目而言，采用 MongoDB 可以直接在题目文档中保存题目类型及其对应配置，避免为了组织这些紧密关联的配置而设计过多关联结构。

#### 3.6.2 配置数据具有较强的对象关联性

选项、校验条件和跳转规则都服务于具体题目。后端处理题目时，通常需要一起读取这些配置。

MongoDB 可以通过嵌入式文档和数组，将这些配置组织在同一个题目文档中。后端取得题目文档后，可以根据题目类型读取相应配置，再调用对应的校验和跳转处理逻辑。

如果采用多张关联表的设计，后端可能需要额外执行关联查询或组装操作。当然，也可以通过关系数据库的 JSON 字段实现类似的文档结构，但这样也说明，具体的选型应当根据数据特点和开发目标，而不是简单比较数据库名称。

#### 3.6.3 需要考虑的另一面

关系数据库在强关系约束、复杂关联查询和事务处理等方面具有成熟的能力。如果系统的重点是复杂报表、大量跨实体关联查询，或者需要频繁依靠外键约束维护多表关系，关系数据库可能同样具有优势。

本系统的数据关系虽然明确，但题目配置具有一定的灵活性，而且课程要求重点考察 MongoDB 的数据建模能力。因此，我选择使用 MongoDB 来表达题目配置，并通过后端逻辑管理集合之间的业务关系。

这一选择的代价是：开发者需要更加主动地实现关联校验和数据完整性检查。也就是说，MongoDB 带来的灵活性并不意味着可以忽略数据约束，而是需要将一部分约束责任明确地放到后端业务层。

### 3.7 为什么 MongoDB 适合本系统

结合上述数据模型，本系统选择 MongoDB 主要有以下几个具体原因。

**第一，文档模型能够自然表达题目配置。**

题目既有共同字段，也有不同题型特有的配置。通过文档结构，可以保留题目的共同信息，同时允许不同题型拥有不同的配置字段，减少为了适应固定字段结构而产生的额外设计。

**第二，嵌入式文档适合保存紧密相关的数据。**

选项、校验规则和跳转规则通常与题目一同读取和维护；一份答卷中的多个答案也共同构成一次提交。使用数组和嵌入式文档能够让这些数据保持在相对完整的业务对象中。

**第三，适合将可变化的业务配置作为数据保存。**

不同问卷的题目、选项、校验条件和跳转规则会有所不同。将这些设置保存到数据库中，可以让后端根据数据配置执行统一的处理逻辑，而不必针对每份问卷编写单独的代码。

**第四，能够通过索引支持常见查询。**

MongoDB 支持单字段索引、组合索引和唯一索引。本系统可以根据用户名查找账号，根据分享码访问问卷，根据创建者查询问卷，以及根据问卷标识查询题目和答卷。

**第五，能够满足当前项目的开发与扩展目标。**

本系统主要面向课程项目，重点是实现完整的问卷业务流程，并验证 MongoDB 在文档建模、灵活配置和数据查询方面的应用。当前采用的集合结构既能够支持已有功能，也为未来增加题目配置提供了一定的灵活性。

不过，MongoDB 并不会自动保证后端业务正确。无论使用哪一种数据库，都需要设计清晰的数据模型、有效的输入校验、合理的权限控制和必要的索引。选择 MongoDB 的依据是它与本项目数据结构的契合程度，而不是认为它在所有方面都优于关系数据库。

### 3.8 数据库与后端架构的配合

我认为，数据库设计不能脱离后端业务逻辑单独评价。即使集合结构合理，如果后端没有正确执行权限检查、数据校验和状态判断，系统仍然可能出现错误数据或越权访问。

因此，本系统采用以业务流程为中心的后端处理方式：数据库负责持久化业务数据，后端负责校验请求、解释配置、执行规则，并决定哪些操作可以进行。

从职责上看，可以将后端处理过程理解为以下几个部分。

#### 3.8.1 请求与身份识别

接口接收客户端请求后，首先检查必要的输入字段，并根据接口要求判断用户是否已登录。

对于问卷管理操作，后端还需要检查当前用户是否为问卷创建者。这样可以避免只依靠客户端提供的问卷 ID 来决定操作权限。

#### 3.8.2 业务状态与关联检查

在修改问卷或题目之前，后端需要确认对应对象存在、归属关系正确，并且当前状态允许执行该操作。

例如，题目管理接口需要遵守问卷草稿状态下才能编辑的业务约束；发布接口需要检查问卷是否满足发布条件；答卷接口则需要确认问卷处于允许提交的状态，并且没有超过截止时间。

这些规则属于业务层的职责，而不是单纯依靠数据库字段就能够自动完成的工作。

#### 3.8.3 根据配置执行校验与跳转

提交答案时，后端需要读取问卷对应的题目和配置，判断答案是否符合题目要求。

对于单选题和多选题，后端需要验证提交的选项是否有效；对于文本题，需要检查文本长度；对于数值题，需要检查数值范围及整数要求；对于必答题，还需要判断答案是否缺失。

如果题目配置了条件跳转，后端需要根据已回答题目的内容判断下一步应当访问哪些题目。跳转规则保存的是条件和目标，而规则如何比较、如何确定跳转结果，仍然由后端程序负责执行。

这种方式让数据库保存具体配置，后端提供统一执行机制，避免将每份问卷的具体题目和规则写死在代码中。

#### 3.8.4 保存答卷与统计结果

通过全部校验后，后端将本次提交组织成一份答卷并保存到 `responses` 集合中。

统计接口再根据问卷标识读取相应答卷，对选择题选项数量、文本答案和数值答案进行汇总。这样，答卷保存和统计计算分别承担不同职责，避免在每次提交时都需要修改问卷基本信息或预先维护一份容易产生不一致的统计结果。

上述处理流程体现了本系统的基本架构思想：**数据库负责保存数据，后端负责维护业务规则，接口负责向客户端提供清晰的业务操作入口。**

需要注意，这里描述的是后端的职责划分和业务处理原则，并不意味着项目已经实现了独立的服务层、仓储层或其他尚未建立的架构模块。具体模块划分仍以项目实际代码为准。

### 3.9 索引设计与查询效率

索引设计需要结合系统实际的查询条件，而不是为所有字段都建立索引。索引能够减少部分查询需要检查的数据量，但也会占用存储空间，并在数据新增或修改时产生维护开销。

本系统建立的主要索引如下：

| 索引 | 主要用途 | 设计理由 |
|---|---|---|
| `users.username` 唯一索引 | 按用户名查找用户 | 支持登录查询，并从数据库层面约束用户名唯一 |
| `surveys.share_code` 唯一索引 | 根据分享码查找问卷 | 支持公开访问入口，并避免不同问卷使用相同分享码 |
| `surveys.creator_id` 与 `created_at` 组合索引 | 查询某个创建者的问卷，并按创建时间排序 | 对应用户查看自己创建的问卷这一常见场景 |
| `questions.survey_id` 与 `order` 唯一组合索引 | 查询问卷题目，并约束同一问卷中的题目顺序值唯一 | 支持按问卷组织题目，同时避免相同问卷内出现重复顺序值 |
| `responses.survey_id` 与 `submitted_at` 组合索引 | 查询某份问卷的答卷，并按提交时间组织结果 | 对应答卷查询和统计的主要访问场景 |

其中，组合索引的字段顺序具有实际意义。以问卷创建者和创建时间组成的组合索引为例，查询通常先限定创建者，再根据创建时间排序，因此索引结构应当与常见查询条件相匹配。

唯一索引也不仅用于提高查询效率，还可以帮助维护数据约束。例如，注册时的重复用户名检查属于业务校验，而唯一索引可以进一步防止并发情况下出现重复用户名。

同样，题目顺序的唯一组合索引只能约束同一问卷内顺序值的唯一性，并不意味着系统已经实现了完整的题目重排机制。题目新增、删除或调整顺序时，后端仍需要合理处理排序值。

需要说明的是，建立索引并不代表所有查询都会自动变快。查询是否能够有效利用索引，还与过滤条件、排序方式、索引字段顺序以及实际数据量有关。对于当前课程项目，这些索引主要服务于已经明确的业务查询场景；如果未来数据量明显增加，可以进一步通过查询分析和性能测试评估索引是否需要调整。

### 3.10 数据完整性、安全性与当前设计的边界

MongoDB 提供灵活的文档模型，但这种灵活性并不意味着可以不进行数据校验。本系统主要通过后端校验、关联检查和索引共同维护数据的有效性。

在数据输入方面，后端需要检查标题、题型、选项、校验配置和答案等内容，避免无效数据直接进入数据库。

在访问控制方面，后端需要区分公开访问和需要登录的操作。例如，分享链接用于访问已发布且仍然有效的问卷；问卷管理和统计操作则需要检查用户身份及其管理权限。

在数据关联方面，后端需要确认题目属于指定问卷、答卷对应的题目有效，并且提交内容符合问卷当前的状态和跳转规则。

在数据库约束方面，唯一索引能够约束用户名、分享码和同一问卷中的题目顺序值，但它不能代替所有业务校验。例如，索引本身不能判断问卷是否已经关闭，也不能判断某个答案是否满足题目的必答要求。

另外，本系统在统计时通过答卷数据进行汇总，因此统计结果依赖于答卷保存和查询逻辑的正确性。如果未来需要处理更大规模的数据，可以考虑增加统计缓存、预计算结果或更系统的聚合查询，但这些优化需要根据实际性能需求决定，不应在当前报告中将尚未实现的功能描述为已有能力。

通过明确这些边界，可以更准确地说明本系统的设计能力：MongoDB 提供数据组织和索引机制，后端负责实施具体的业务约束，两者配合完成问卷数据的管理。

### 3.11 小结

本系统的 MongoDB 数据库设计以实际业务实体和访问方式为依据，将用户、问卷、题目和答卷分别存储在独立集合中，同时将选项、校验配置、跳转规则和单份答卷中的答案组织为嵌入式数据。

采用这种结构的主要原因，是不同业务实体具有不同的生命周期和增长特点，而题目配置与单次答卷中的内容又具有较强的内部关联性。通过独立集合与嵌入式文档相结合，可以在数据职责清晰、文档结构灵活和查询组织简洁之间取得平衡。

在技术选型方面，关系数据库同样能够实现本系统的业务功能，但 MongoDB 的文档模型更方便直接表达不同题型的差异化配置，也符合本项目学习和实践文档型数据库的目标。

在后端架构方面，数据库负责保存业务数据和必要的索引，后端负责权限判断、状态管理、数据关联校验、答案验证、条件跳转和统计计算。设计中既利用了 MongoDB 的灵活性，也考虑到其灵活数据模型需要由应用程序补充维护的完整性约束。

总体而言，本系统并不是单纯地将数据存入 MongoDB，而是根据问卷业务的特点选择数据模型，并让数据库结构与后端处理流程相互配合。这样的设计既能够满足当前系统的功能需求，也为后续扩展题型和配置规则保留了空间。

## 四、跳转设计

系统支持根据用户的答案决定后续需要回答的题目。跳转规则保存在题目数据中，而不是将具体跳转条件固定写在程序中。

当前支持的跳转判断包括：

- **单选题：** 根据所选选项 ID 匹配跳转规则。
- **多选题：** 根据所选选项集合判断是否满足跳转条件。
- **数值题：** 支持等于、不等于、大于、大于等于、小于和小于等于等比较条件。

系统按照题目顺序计算答题路径。匹配到有效跳转规则时，跳转目标必须属于当前问卷，并且位于当前题目之后；否则按正常题目顺序继续处理。文本题不支持条件跳转。

提交答案时，系统会根据实际答题路径判断哪些题目有效，并拒绝针对被跳过题目提交的答案，避免答卷内容与跳转规则不一致。

## 五、校验设计

系统在题目配置和答卷提交两个阶段进行校验。

### 5.1 题目配置校验

创建或修改题目时，系统会检查题目标题、题目类型、选项、必答设置、校验配置和跳转规则等内容。

主要校验规则包括：

- 题目标题不能为空，且不能超过规定长度。
- 题目类型必须属于系统支持的类型。
- 单选题和多选题至少配置两个选项，选项内容不能为空且不能重复。
- 必答设置必须为布尔值。
- 多选题可以设置最少选择数、最多选择数或精确选择数，并检查配置是否合理。
- 文本题可以设置最小长度和最大长度。
- 数值题可以设置最小值、最大值及是否要求整数。
- 跳转规则必须具有合法结构，选项跳转规则引用的选项必须存在。

### 5.2 答案提交校验

用户提交答卷时，系统会检查问卷状态、截止时间、题目归属、答案格式及具体题型对应的约束。

例如，单选题答案必须对应有效选项；多选题答案必须是合法选项组成的列表，不能包含重复选项，并且需要满足选择数量限制；文本题答案必须符合文本类型和长度限制；数值题答案必须是有限数值，并符合配置的范围和整数要求。

对于必答题，系统会检查是否提供有效答案；对于跳转逻辑中已经跳过的题目，系统会拒绝其答案。

### 5.3 后端校验的必要性

前端校验可以帮助用户及时发现输入错误，但不能代替后端校验。客户端提交的数据可能来自修改后的请求，也可能绕过正常的页面操作，因此后端不能默认所有输入都可信。

本系统在题目配置阶段检查题目类型、选项和校验规则，在答卷提交阶段则根据数据库中保存的题目配置重新验证答案。这样可以避免仅依赖客户端判断答案是否合法。

对于条件跳转，后端还需要结合实际答题路径检查提交内容，避免用户通过直接构造请求提交已被跳过题目的答案。对于问卷管理接口，后端同样需要检查登录身份、问卷归属和当前状态。

通过将输入校验、权限检查和业务规则执行放在后端，可以使系统的数据约束不依赖于特定的前端页面，提升业务处理的可靠性。

## 八、遇到的问题及解决方法

### 8.1 不同题型的数据结构存在差异

不同题型需要保存不同的选项和校验配置，如果使用完全相同的固定字段处理所有题型，容易造成数据结构不清晰或校验规则混乱。

解决方法：为题目设置统一的类型字段，并通过校验配置字段保存不同题型所需的规则；在后端根据题目类型执行相应校验。

### 8.2 条件跳转会影响答案的有效性

当题目配置了跳转规则后，并不是问卷中的所有题目都必然需要回答。如果只检查答案格式而不检查实际答题路径，可能出现对已跳过题目提交答案的情况。

解决方法：在提交答卷时根据题目顺序和跳转规则计算有效答题路径，并校验提交的答案是否属于该路径。

### 8.3 数据关联与查询需要兼顾一致性和效率

用户、问卷、题目和答卷分别存储后，需要通过标识字段建立逻辑关联，同时保证常用查询能够有效执行。

解决方法：使用用户 ID、问卷 ID 和题目 ID 等标识关联业务数据，并为用户名、分享码、题目顺序和答卷查询等场景建立相应索引。

### 8.4 需要验证业务逻辑是否符合预期

仅检查接口能否返回响应，无法充分验证问卷创建、答案校验和跳转等业务规则是否正确。

解决方法：使用 pytest 编写 API 自动化测试，对主要业务流程和部分异常输入进行验证。当前 9 项自动化测试全部通过；未覆盖的业务分支仍可通过后续测试进一步完善。

## 九、总结

本项目完成了基于 MongoDB 的在线问卷系统主要后端功能，包括用户认证、问卷管理、题目管理、条件跳转、答案校验、答卷提交和结果统计。

通过将不同业务实体存储在独立集合中，并使用嵌入式文档表示题目选项、校验配置和跳转规则，系统能够支持不同题型的差异化数据结构。通过 API 自动化测试，对主要业务流程进行了验证，当前测试结果为 9 项全部通过。

本项目加深了对 MongoDB 文档建模、索引设计、后端 API 开发、条件业务逻辑和自动化测试的理解。后续仍可针对尚未充分覆盖的边界条件和异常分支进一步完善测试。
