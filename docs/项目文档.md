# 基于 MongoDB 的问卷系统——项目文档

## 一、系统概述

### 1.1 项目背景与目标

本项目是“当代数据管理系统”课程大作业，目标是设计并实现一个基于 MongoDB 的简化在线问卷系统。系统围绕问卷创建、题目配置、问卷发布、答卷提交和统计分析等环节展开，使问卷创建者能够管理自己的问卷，并通过分享码提供问卷访问入口。

项目重点在于将数据库设计与实际业务规则结合起来。问卷、题目和答卷之间存在关联关系；不同题型具有不同的答案校验规则；条件跳转会改变正常答题顺序；统计结果则依赖已保存的答卷数据。因此，系统需要同时考虑数据组织、权限管理、业务校验和测试验证。

### 1.2 设计思路

系统采用 Flask 作为后端框架，通过 PyMongo 访问 MongoDB，主要遵循以下设计原则：

1. **按业务对象组织数据。** 用户、问卷、题目和答卷分别保存在独立集合中，便于按业务职责查询和维护。
2. **由后端执行关键校验。** 用户认证、问卷状态、题目配置、答案内容和答题路径均由后端接口进行检查，避免仅依赖客户端校验。
3. **分离题目配置与答卷数据。** 题目保存问卷的规则和内容，答卷保存某一次实际提交的结果。
4. **通过测试验证业务行为。** 通过自动化测试和手工接口实验验证主要业务行为。自动化测试覆盖认证、问卷创建与发布、题目校验、答卷提交、统计及单选题条件跳转；手工实验进一步检查部分权限限制、截止时间、不同题型跳转和统计行为。上述测试不代表所有业务分支均已覆盖。

## 二、系统说明

### 2.1 总体架构

系统使用 Flask 接收和处理 HTTP 请求，各路由模块分别负责认证、问卷管理、题目管理及答卷处理。需要访问数据库时，通过统一的数据库连接模块操作 MongoDB。

```text
用户 / HTTP 请求
        |
        v
Flask 应用（app/__init__.py）
        |
        +---- 用户认证（app/routes/auth.py）
        |
        +---- 问卷管理（app/routes/surveys.py）
        |
        +---- 题目管理（app/routes/questions.py）
        |
        +---- 答卷提交（app/routes/responses.py）
        |
        v
MongoDB 连接模块（app/db.py）
        |
        v
users / surveys / questions / responses
```

`run.py` 是应用启动入口；`app/__init__.py` 创建 Flask 应用并注册路由；`app/db.py` 读取数据库配置并创建 MongoDB 客户端；`app/init_db.py` 负责创建集合和索引。

应用启动与数据库初始化相互独立。`create_app()` 不会自动执行数据库初始化脚本，因此首次运行或部署时，应先确认 MongoDB 服务可用，再执行初始化脚本。

### 2.2 模块职责

| 模块 | 主要职责 |
|---|---|
| `run.py` | 启动 Flask 应用 |
| `app/__init__.py` | 创建应用、配置密钥、注册路由、提供首页与健康检查 |
| `app/db.py` | 读取环境变量、创建 MongoDB 客户端、选择目标数据库 |
| `app/init_db.py` | 创建所需集合和索引 |
| `app/routes/auth.py` | 用户注册、登录、退出登录和登录状态查询 |
| `app/routes/surveys.py` | 问卷创建、列表查询、发布、关闭、截止时间设置、分享访问和统计 |
| `app/routes/questions.py` | 题目查询、创建、修改和删除 |
| `app/routes/responses.py` | 答卷提交、答案校验和条件跳转路径验证 |
| `tests/test_api.py` | 接口自动化测试 |

### 2.3 配置与运行方式

项目通过环境变量配置 Flask 密钥和 MongoDB 连接信息，主要包括：

- `SECRET_KEY`：Flask 会话等功能使用的签名密钥。
- `MONGO_URI`：MongoDB 服务连接地址。
- `MONGO_DB_NAME`：项目使用的数据库名称。

数据库连接模块使用 `python-dotenv` 读取环境变量，并通过 PyMongo 创建客户端。当前开发环境默认连接本机 MongoDB，数据库名称默认为 `survey_system`；自动化测试使用 `survey_system_test`。

在开发环境中将 `SECRET_KEY` 配置为独立且足够安全的值。代码中的开发默认密钥仅适用于本地开发，不直接用于正式部署。

## 三、MongoDB 数据库设计

### 3.1 数据建模思路

系统的主要业务关系包括：用户可以创建多份问卷；每份问卷可以包含多道题目；每次提交会形成一份答卷；答卷中的答案通过题目标识与对应题目关联。

本项目将用户、问卷、题目和答卷保存在独立集合中，而不是把所有信息嵌入单个大型文档。这样可以分别执行问卷查询、题目维护、答卷保存和统计操作，也便于为常用查询建立索引。

这种设计需要在关联查询时通过业务标识连接相关记录。MongoDB 的标识关联本身并不等同于关系型数据库的外键约束，因此相关记录是否存在、用户是否有权操作等问题仍需由业务逻辑检查。

### 3.2 集合设计

| 集合 | 保存内容 | 主要用途 |
|---|---|---|
| `users` | 用户名、密码哈希等 | 用户注册、登录和身份识别 |
| `surveys` | 创建者、标题、描述、匿名设置、状态、分享码、截止时间及时间字段 | 问卷管理与生命周期控制 |
| `questions` | 所属问卷、题目标题、题型、选项、必填规则、校验配置、跳转规则及顺序 | 题目配置与答题规则 |
| `responses` | 所属问卷、答卷答案、提交者标识及提交时间 | 保存答卷和提供统计数据 |

MongoDB 文档还具有自动生成的 `_id`。具体字段是否存在、默认值及可选字段，以当前路由代码实际写入的数据为准。

### 3.3 集合之间的关联

```text
users
  |
  | 用户标识
  v
surveys
  |
  +---- questions
  |       通过 survey_id 关联
  |
  +---- responses
          通过 survey_id 关联
```

问卷记录中的创建者标识用于区分问卷归属。题目通过 `survey_id` 关联问卷；答卷同样保存问卷标识，以便按问卷查询提交记录并计算统计结果。

对于匿名问卷，答卷中的 `respondent_id` 保存为 `None`；非匿名问卷则保存提交用户的标识。匿名设置影响答卷中提交者标识的保存方式，但不能据此推断系统实现了额外的身份匿名审计或防追踪机制。

### 3.4 索引设计

`app/init_db.py` 为系统创建以下六个索引：

| 集合 | 索引名称 | 索引字段与作用 |
|---|---|---|
| `users` | `uq_users_username` | `username` 唯一索引，避免用户名重复 |
| `surveys` | `uq_surveys_share_code` | `share_code` 唯一索引，避免分享码重复 |
| `surveys` | `idx_surveys_creator_created` | `creator_id` 与 `created_at` 组合索引，支持按创建者和时间查询问卷 |
| `questions` | `uq_questions_survey_order` | `survey_id` 与 `order` 组合唯一索引，约束同一问卷内题目顺序不重复 |
| `responses` | `idx_responses_survey_submitted` | `survey_id` 与 `submitted_at` 组合索引，支持按问卷查询答卷及其提交时间 |
| `responses` | `uq_responses_submission_key` | `submission_key` 稀疏唯一索引，对包含该字段的记录施加唯一性约束 |

索引能够提升特定查询的效率或约束部分重复数据，但也会增加写入时维护索引的成本，因此应围绕实际查询场景建立索引。

需要特别说明：`submission_key` 稀疏唯一索引不等于已经实现防重复填写。当前答卷提交逻辑没有写入该字段，且实际实验验证了同一用户可以多次提交。因此，本项目当前不应宣称具有强制禁止重复提交的功能。

### 3.5 数据组织与统计功能

系统将每次提交保存为独立的答卷记录。统计功能根据问卷标识查询答卷，再按照题型解释答案：

- 单选题：统计各选项被选择的次数。
- 多选题：分别统计各选项在答卷中出现的次数。
- 文本题：展示已保存的文本答案。
- 数字题：对符合要求的数字答案计算平均值等统计结果。

多选题中，一份答卷可以选择多个选项，因此各选项的选择次数之和可能大于答卷总数。统计时应区分答卷数量和选项选择次数。

## 四、问卷业务流程与状态管理

### 4.1 业务流程

```text
用户注册 / 登录
       |
       v
创建问卷
       |
       v
添加并配置题目
       |
       v
发布问卷
       |
       v
通过分享码访问
       |
       v
填写并校验答案
       |
       v
提交答卷并保存
       |
       v
查询统计结果
```

创建者负责配置和管理问卷；填写者通过分享码定位问卷，并按照题目规则提交答案。系统需要同时检查问卷状态、访问条件、答案内容和答题路径，而不能仅凭客户端提供的标识就接受操作。

### 4.2 权限控制

问卷管理接口通过当前登录用户标识和问卷创建者标识检查操作权限。用户查询问卷列表时，只能查询属于自己的问卷；发布、关闭、设置截止时间及查看统计等管理操作也需要验证问卷归属。

在手工实验中，第二个用户尝试修改第一个用户创建的问卷截止时间时，接口返回 HTTP 404，提示问卷不存在或用户没有管理权限。这说明当前接口会拒绝该越权操作。

分享访问与问卷管理权限不同。分享码用于定位问卷，但能否访问和提交仍受发布状态、关闭状态及截止时间等条件限制。

### 4.3 发布、关闭与截止时间

问卷创建后初始状态为 `draft`。发布接口要求问卷至少包含一道题目；发布成功后，问卷状态变为 `published`。关闭接口只允许关闭处于 `published` 状态的问卷。

截止时间设置接口只允许对草稿问卷操作。请求可以提供 ISO 8601 格式的时间，也可以将 `deadline` 设为 `null` 以清除截止时间。时间字符串需要包含时区信息；格式错误、缺少时区或设置为过去的时间会被拒绝。

手工实验验证了以下行为：

1. 设置已经过去的截止时间会被拒绝。
2. 设置未来的截止时间可以成功。
3. 将截止时间清空可以成功。
4. 已关闭的问卷不能提交答卷。

因此，问卷能否填写不只取决于分享码是否存在，还取决于问卷状态和截止时间等条件。

## 五、题目模型与输入校验设计

### 5.1 支持的题型

系统当前支持四类题目：

- `single_choice`：单选题。
- `multiple_choice`：多选题。
- `text`：文本题。
- `numeric`：数字题。

题目数据包含所属问卷标识、标题、题型、选项、必填设置、校验配置、跳转规则、顺序及创建和更新时间等字段。

题目管理操作要求用户登录，并且目标问卷必须属于当前用户且处于草稿状态。题目列表查询也要求用户具有相应的问卷管理权限。

### 5.2 题目配置校验

创建或修改题目时，后端会根据题型检查配置内容。

| 题型 | 主要配置及校验 |
|---|---|
| 单选题 | 标题非空；选项列表至少包含两个非空且不重复的选项 |
| 多选题 | 标题和选项校验；支持最少选择数、最多选择数或固定选择数配置，并检查这些限制之间是否一致 |
| 文本题 | 标题非空；可配置最短和最长文本长度，并检查最小值不大于最大值 |
| 数字题 | 标题非空；可配置最小值、最大值和是否要求整数，并检查范围配置是否合理 |

题目标题需要是非空字符串，最大长度为 500。选项型题目将选项规范化保存为包含 `option_id` 和 `text` 的对象，便于答卷保存选项标识而不是依赖选项显示文本。

校验配置必须是字典类型。数量和长度限制需要是非负整数；布尔值不能被当作普通整数限制。数字范围值必须为数字且不能是布尔值，最小值不能大于最大值。

### 5.3 答案校验

答卷提交时，后端根据题目配置检查答案：

- **必填规则：** 必填题不能提交空答案；选填题允许空答案。
- **单选题：** 答案必须是有效的选项标识。
- **多选题：** 答案必须是选项标识列表，选项必须有效且不能重复，并且选择数量需要符合配置限制。
- **文本题：** 答案必须为字符串，并满足配置的长度限制。
- **数字题：** 答案必须为有限数字，不能是布尔值，并且需要满足范围和整数要求。

后端校验可以防止调用者绕过页面限制，直接构造不符合题目配置的 HTTP 请求。

### 5.4 校验实验

手工实验验证了以下非法输入会被拒绝：

- 数字题最大值设置为 10，提交 11 时被拒绝，并提示数值不能大于 10。
- 多选题最多允许选择 2 个选项，提交 3 个选项时被拒绝。
- 必填文本题提交空内容时被拒绝。

这些实验表明，系统在保存答卷前执行题目校验，而不是直接保存所有收到的请求。

## 六、条件跳转设计

### 6.1 设计目标

条件跳转用于根据前面题目的答案决定后续答题路径。例如，只有选择特定选项的填写者才需要回答某个后续问题。

条件跳转不仅需要决定下一道题，还需要在提交时检查答案列表是否符合预期路径。否则，调用者可能提交本应跳过的题目，或者通过构造请求绕过应回答的题目。

### 6.2 跳转规则

系统支持以下跳转判断：

- 单选题：根据所选选项标识判断是否触发规则。
- 多选题：根据答案列表是否包含指定选项标识判断是否触发规则。
- 数字题：支持 `eq`、`ne`、`gt`、`gte`、`lt`、`lte` 等数值比较运算符。

跳转规则中包含目标题目标识。提交时，系统按照题目顺序计算实际答题路径，并使用第一个匹配且目标题存在于当前问卷、位于当前题目之后的跳转规则。未触发有效跳转时，继续按照正常题目顺序前进。

当前实现只支持向后跳转，不支持跳转到前面的题目。文本题不支持条件跳转。无效或不属于当前问卷的目标题不会成为有效跳转目标。

### 6.3 跳转与提交校验

后端根据答案计算当前问卷的有效答题路径，并拒绝提交不符合路径的答案。对于被跳过的题目，即使客户端提供了该题答案，提交也会被拒绝。对于有效路径中的必填题，仍然需要满足必填规则。

这使跳转路径校验与答案校验共同发挥作用：路径校验决定哪些题目应该出现，题目校验决定答案是否有效。

### 6.4 跳转实验

手工实验验证了三种题型的跳转行为：

1. **单选题跳转：** 选择触发跳转的选项后，可以跳过中间题并提交；如果仍提交被跳过题目的答案，则返回 HTTP 400。
2. **数字题跳转：** 达到配置阈值时跳转到后续题目，低于阈值时按正常顺序答题。
3. **多选题跳转：** 选择触发跳转的选项后，可以跳过中间题；提交被跳过题目的答案会被拒绝；未触发跳转时可以按正常顺序提交。

这些实验验证了跳转规则不仅可以保存，还会影响实际提交路径。

## 七、答卷提交与统计设计

### 7.1 答卷提交流程

答卷提交的主要处理过程如下：

```text
接收答卷请求
      |
      v
检查登录状态与请求结构
      |
      v
检查问卷发布状态及截止时间
      |
      v
校验答案所属题目与重复题目标识
      |
      v
计算有效答题路径
      |
      v
校验有效路径中的答案
      |
      v
保存本次答卷记录
      |
      v
返回提交结果
```

当前答卷提交接口要求用户登录。请求体需要包含 `answers` 列表；题目标识必须属于目标问卷，不能重复，并且每个答案项必须包含 `answer` 字段。校验通过后，系统保存答卷并返回提交结果。

### 7.2 答卷数据结构

每份答卷记录包含以下主要字段：

- `survey_id`：所属问卷标识。
- `respondent_id`：提交用户标识；匿名问卷保存为 `None`。
- `answers`：本次提交中有效的答案列表。
- `submitted_at`：提交时间。

每个答案项保存 `question_id` 和 `answer`。提交记录还具有 MongoDB 自动生成的 `_id`。

### 7.3 重复提交行为

当前实现允许同一用户多次提交同一份仍可填写的问卷。手工实验中，同一用户连续提交两次均成功，并生成独立答卷记录。

因此，项目当前的业务行为是允许重复提交，而不是限制每个用户只能填写一次。虽然数据库初始化脚本定义了 `submission_key` 稀疏唯一索引，但当前提交逻辑没有写入该字段，所以该索引没有构成有效的防重复提交机制。

如果后续需要限制重复填写，需要进一步明确业务规则，并在提交逻辑和数据库约束中共同实现。

### 7.4 统计逻辑

统计接口要求问卷创建者登录，并且只能查询自己问卷的统计结果。统计数据来源于该问卷已保存的答卷记录。

统计逻辑按题型处理：

- 单选题：统计各选项被选择的次数。
- 多选题：分别统计各选项出现的次数。
- 文本题：整理已提交的文本答案。
- 数字题：统计有效数字答案的数量及平均值等结果。

空答案不参与相应内容统计；数字统计只处理有限数字，并排除布尔值。多选题各选项的选择次数之和可能大于答卷总数。

### 7.5 统计实验

手工测试中，一份包含单选、多选、文本和数字题的问卷成功提交了一份答卷，统计结果与提交内容一致：

- 单选题所选选项的计数为 1。
- 多选题中，MongoDB 和 MySQL 的选择次数各为 1，PostgreSQL 的选择次数为 0。
- 文本答案中的中文内容能够正确保存和显示。
- 数字题的平均值为 8。

该实验验证了上述题型在当前测试数据下的保存与统计行为，但不代表所有数据规模和异常条件均已测试。

## 八、API 接口说明

### 8.1 接口总览

项目使用 Flask Blueprint 组织 API。以下路径均为相对于本地服务地址的路径，实际请求还需要包含服务器地址，例如 `http://127.0.0.1:5000`。

| 方法 | 路径 | 权限要求 | 主要用途 |
|---|---|---|---|
| `GET` | `/` | 无 | 查询后端运行信息 |
| `GET` | `/health` | 无 | 检查 MongoDB 连接状态 |
| `POST` | `/api/auth/register` | 无 | 注册用户 |
| `POST` | `/api/auth/login` | 无 | 用户登录 |
| `POST` | `/api/auth/logout` | 登录会话 | 退出登录 |
| `GET` | `/api/auth/me` | 登录状态查询 | 查询当前会话的用户状态 |
| `POST` | `/api/surveys` | 登录 | 创建问卷 |
| `GET` | `/api/surveys` | 登录 | 查询当前用户的问卷列表 |
| `POST` | `/api/surveys/<survey_id>/publish` | 问卷创建者 | 发布草稿问卷 |
| `POST` | `/api/surveys/<survey_id>/close` | 问卷创建者 | 关闭已发布问卷 |
| `PUT` | `/api/surveys/<survey_id>/deadline` | 问卷创建者 | 设置或清除草稿问卷的截止时间 |
| `GET` | `/api/surveys/share/<share_code>` | 无登录要求 | 通过分享码获取已发布且未过期的问卷及题目 |
| `GET` | `/api/surveys/<survey_id>/stats` | 问卷创建者 | 查询问卷统计 |
| `POST` | `/api/surveys/<survey_id>/questions` | 问卷创建者，且问卷为草稿 | 创建题目 |
| `GET` | `/api/surveys/<survey_id>/questions` | 问卷创建者 | 查询题目列表 |
| `PUT` | `/api/surveys/<survey_id>/questions/<question_id>` | 问卷创建者，且问卷为草稿 | 修改题目 |
| `DELETE` | `/api/surveys/<survey_id>/questions/<question_id>` | 问卷创建者，且问卷为草稿 | 删除题目 |
| `POST` | `/api/responses/<share_code>` | 登录 | 提交答卷 |

### 8.2 认证接口

#### 注册：`POST /api/auth/register`

用于创建用户账号。用户名会去除首尾空白，长度要求为 3–30 个字符；密码长度至少为 8 个字符。系统保存密码哈希，而不是直接保存明文密码。重复用户名会被拒绝，返回 HTTP 409。

#### 登录：`POST /api/auth/login`

用于验证用户名和密码，并在成功后建立 Flask 会话。系统通过会话中的 `user_id` 和 `username` 识别当前登录用户。

#### 退出登录：`POST /api/auth/logout`

用于清除当前会话中的登录信息。

#### 查询登录状态：`GET /api/auth/me`

用于查询当前请求是否具有有效登录状态，以及当前用户的相关信息。

### 8.3 问卷管理接口

#### 创建问卷：`POST /api/surveys`

要求用户登录。问卷标题必须是非空字符串，长度不能超过 100；描述默认为空字符串，匿名设置默认为 `false`。新问卷初始状态为 `draft`，系统会生成分享码，并记录创建和更新时间。

#### 查询问卷列表：`GET /api/surveys`

要求用户登录，只返回当前用户创建的问卷，并按创建时间倒序排列。

#### 发布问卷：`POST /api/surveys/<survey_id>/publish`

要求请求用户是问卷创建者，目标问卷处于 `draft` 状态，并且至少包含一道题目。若设置了截止时间，该时间必须晚于当前时间。发布成功后状态变为 `published`，响应中提供用于访问问卷的分享路径。

#### 关闭问卷：`POST /api/surveys/<survey_id>/close`

要求请求用户是问卷创建者，且目标问卷当前处于 `published` 状态。关闭后问卷不再接受新的答卷提交。

#### 设置截止时间：`PUT /api/surveys/<survey_id>/deadline`

要求请求用户是问卷创建者，且问卷处于 `draft` 状态。请求必须包含 `deadline` 字段：提供带时区的 ISO 8601 时间字符串可以设置截止时间；提供 `null` 可以清除截止时间。格式错误、没有时区或时间不晚于当前时间的值会被拒绝。

#### 分享访问：`GET /api/surveys/share/<share_code>`

通过分享码查询问卷。该接口不要求登录，但问卷必须处于允许访问的发布状态且未过期。响应包含问卷信息和按顺序排列的题目数据，包括题目标识、标题、类型、必填设置、选项、顺序、校验配置和跳转规则等字段。

#### 查询统计：`GET /api/surveys/<survey_id>/stats`

要求请求用户是问卷创建者。接口根据已保存的答卷记录计算各题型的统计结果。

### 8.4 题目管理接口

题目管理接口的共同要求是：用户已登录，目标问卷属于当前用户，并且创建、修改和删除操作的问卷必须处于 `draft` 状态。

| 方法与路径 | 主要用途 |
|---|---|
| `POST /api/surveys/<survey_id>/questions` | 创建题目；根据题型校验标题、选项、校验配置和跳转规则 |
| `GET /api/surveys/<survey_id>/questions` | 查询问卷题目列表 |
| `PUT /api/surveys/<survey_id>/questions/<question_id>` | 修改题目配置 |
| `DELETE /api/surveys/<survey_id>/questions/<question_id>` | 删除题目并重新整理剩余题目顺序 |

新建题目的顺序由现有题目数量及顺序确定。删除题目后，系统会重新整理剩余题目的顺序，以满足同一问卷内题目顺序唯一的索引约束。

### 8.5 答卷提交接口

#### `POST /api/responses/<share_code>`

该接口要求用户登录，请求体为 JSON 对象，且必须包含 `answers` 列表。每个答案项需要包含题目标识和 `answer` 字段。

接口会依次检查请求结构、问卷是否可填写、题目标识是否属于目标问卷、是否重复提交同一题目标识、答案是否符合有效答题路径，以及题目本身的校验规则。全部检查通过后，系统保存答卷并返回 HTTP 201。

当前实现中，未登录请求会返回 HTTP 401；找不到可提交的已发布问卷或问卷已经关闭时会返回 HTTP 404；超过截止时间会被拒绝。答案内容或答题路径不合法时会返回 HTTP 400。

### 8.6 首页与健康检查

`GET /` 用于返回后端运行信息和当前数据库名称。`GET /health` 会执行 MongoDB 连接检查：连接正常时返回 HTTP 200，数据库连接异常时返回 HTTP 503。

### 8.7 常见错误及其含义

| 场景 | 已验证或实现的行为 | 含义 |
|---|---|---|
| 重复注册用户名 | HTTP 409 | 用户名已存在 |
| 未登录提交答卷 | HTTP 401 | 需要先登录 |
| 提交非法答案 | HTTP 400 | 答案不符合题目配置 |
| 提交与跳转路径不一致的答案 | HTTP 400 | 提交内容包含不应回答的题目 |
| 修改他人问卷 | HTTP 404 | 问卷不存在或当前用户无管理权限 |
| 提交已关闭问卷 | HTTP 404 | 问卷当前不可提交 |
| 设置过去的截止时间 | HTTP 400 | 截止时间不符合要求 |
| MongoDB 连接异常 | `/health` 返回 HTTP 503 | 数据库健康检查失败 |

具体错误消息以对应路由的实际返回内容为准。本节说明主要接口行为，不应代替源代码中所有错误分支的完整返回 JSON。


## 九、关键逻辑说明

### 9.1 问卷状态与权限控制

问卷创建后初始状态为 `draft`。只有问卷创建者才能管理自己的问卷，且题目的创建、修改和删除要求问卷处于草稿状态。发布时，系统检查问卷是否至少包含一道题目；发布成功后状态变为 `published`。已发布问卷可以关闭，关闭后不能继续提交答卷。

### 9.2 题目与答案校验

系统根据题目类型执行不同的校验规则。单选题检查选项是否合法；多选题还需要检查选项数量限制；文本题检查文本类型和长度；数字题检查数值范围和整数要求。必填规则与题型校验共同决定答案是否有效，校验不通过的请求不会作为成功答卷保存。

### 9.3 条件跳转与有效答题路径

系统根据单选题、多选题或数字题的答案判断是否触发跳转。后端按照题目顺序计算有效答题路径，并检查提交的答案是否符合该路径。若某道题因跳转而被跳过，客户端仍提交该题答案时，系统会拒绝此次提交。当前实现只支持跳转到后续题目。

### 9.4 答卷保存与统计计算

每次成功提交都会生成独立的答卷记录。答卷保存所属问卷、提交者标识、答案列表和提交时间。统计时，系统根据问卷标识查询答卷，并按题型计算选项次数、文本答案和数字平均值等结果。当前实现允许同一用户多次提交，因此统计中的答卷数量代表提交记录数量，而不等同于独立用户数量。

### 9.5 截止时间与问卷可访问性

发布前可以设置或清除截止时间。截止时间必须是带时区的 ISO 8601 时间，且必须晚于当前时间。分享访问和答卷提交均需要检查问卷状态及截止时间，防止已关闭或已过期的问卷继续接受答卷。

### 9.6 关键逻辑的验证方式

项目通过自动化测试和手工接口实验验证上述逻辑，包括非法答案拦截、问卷管理权限、截止时间处理、单选与多选及数字题跳转，以及答卷统计。测试结果仅说明已执行场景的行为，不代表所有异常情况均已覆盖。

## 十一、当前设计的边界与后续改进

本项目重点实现课程要求下的问卷核心功能，包括 MongoDB 数据组织、用户认证、问卷管理、题目配置、条件跳转、答卷提交和统计。

当前实现仍有以下可以继续改进的方面：

1. **补充边界测试。** 增加复杂跳转组合、空数据统计、异常数据库连接及并发提交等测试。
2. **加强数据一致性管理。** 进一步明确删除问卷、修改题目和保留历史答卷时的数据处理规则。
3. **完善接口响应文档。** 为每个 API 补充完整请求 JSON、成功响应 JSON、错误响应 JSON 和全部状态码，便于联调。
4. **明确重复提交策略。** 当前允许同一用户多次提交，`submission_key` 索引尚未形成有效的重复提交限制。若业务要求改变，需要同步调整提交逻辑、数据模型和索引。
5. **优化统计查询。** 随着数据量增加，可以依据实际查询负载评估索引及聚合查询方案。
