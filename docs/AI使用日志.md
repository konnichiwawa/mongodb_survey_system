### 3.2 MongoDB 数据模型设计与结构选择

**使用工具：** ChatGPT

**Prompt（整理后的代表性提示词）：**

> 请帮我设计适用于问卷系统的 MongoDB 数据模型。要求使用 MongoDB，不使用关系型数据库，不使用现成问卷框架。系统包含用户、问卷、题目和答卷。请说明哪些数据应该独立存储，哪些数据适合嵌入文档，并解释这样设计的原因、索引需求，以及这种结构与传统关系型数据库表结构的区别。

**Result：**

结合当前项目的实际代码，系统采用四个集合组织主要业务数据：

| 集合 | 主要存储内容 | 设计目的 |
|---|---|---|
| `users` | 用户账号及认证相关信息 | 独立管理用户身份信息 |
| `surveys` | 问卷标题、描述、创建者、状态、分享码、截止时间等 | 管理问卷的基本信息和生命周期 |
| `questions` | 问题标题、题型、选项、顺序、校验规则、跳转规则等 | 独立管理每道题的内容和配置 |
| `responses` | 问卷关联信息、答题内容、提交时间和答题者关联信息 | 保存答卷，供后续查询与统计 |

题目和答卷通过 `survey_id` 关联对应问卷。题目中的选项、校验规则和跳转规则则作为题目文档中的嵌入字段保存。

例如，题目文档中包含以下结构：

```python
question = {
    "survey_id": survey_id,
    "title": title,
    "type": question_type,
    "options": options,
    "required": required,
    "validation": validation,
    "jump_rules": jump_rules,
    "order": order,
}
```

以上代码用于展示当前项目采用的数据组织思路。实际创建题目时，`app/routes/questions.py` 会将经过校验的字段与问卷 ID、题目顺序和时间信息组合后写入 MongoDB。

**是否修改：**

有修改。AI 对 MongoDB 数据模型的分析作为数据库设计的参考，我结合问卷系统的业务需求和实际代码，对集合划分、字段组织方式和索引配置进行了梳理与完善，没有直接照搬通用的数据模型方案。

**修改内容：**

1. **明确集合划分及职责。** 根据系统实际功能，将数据分别存储在 `users`、`surveys`、`questions` 和 `responses` 四个集合中。其中，`users` 保存用户信息，`surveys` 保存问卷基本信息，`questions` 保存每道题目的内容和配置，`responses` 保存用户提交的作答记录。这样可以避免将用户、问卷、题目和所有答卷内容全部堆放在同一个集合中。

2. **梳理集合之间的关联。** 题目通过 `survey_id` 关联所属问卷，答卷通过 `survey_id` 关联问卷，并通过 `respondent_id` 记录作答用户。通过这些关联字段，后端可以查询某份问卷的题目、提交记录及相关统计数据，同时减少不同集合之间不必要的数据重复。

3. **区分嵌入式数据与独立集合。** 对于题目选项、校验规则和条件跳转规则等与单道题目紧密相关的配置，将其放在题目文档内部，便于读取题目时一并获取相关配置；对于题目、用户和答卷等具有独立管理和查询需求的数据，则分别存储在不同集合中。这样兼顾了数据组织的清晰性和 MongoDB 文档结构的灵活性。

4. **补充索引设计及其用途。** 根据实际代码中的索引配置，使用用户名唯一索引避免用户名重复，使用问卷分享码唯一索引避免分享码冲突，使用 `survey_id` 和 `order` 的组合唯一索引约束同一问卷内的题目顺序，并为答卷查询配置问卷标识和提交时间相关的索引，以支持按问卷查询提交记录并按时间排序。

5. **检查设计说明与代码的一致性。** 在完善项目文档时，将集合职责、关联字段、嵌入式配置和索引设计分别与实际代码对应，避免文档只介绍 MongoDB 的一般特点，却没有说明本项目为什么采用这些具体结构。

**我的设计考虑：**

我认为不适合将用户、问卷、题目和所有答卷都存放在一个大型文档或一个集合中。它们的用途和数据增长方式不同：问卷需要管理发布状态，题目需要独立维护，答卷则会随着提交不断增加。分开存储更便于按问卷查询题目、保存答卷和开展统计。

另一方面，也没有必要将每个选项和每条校验规则都拆成独立集合。选项、校验规则和跳转规则通常与题目一起读取，嵌入题目文档可以让相关配置集中保存，并减少为了读取一道题而进行的额外查询。

与传统关系型数据库设计相比，MongoDB 可以通过文档结构保存题目中的嵌套配置，通过 `survey_id` 等字段建立逻辑关联，而不必完全采用多张关系表和大量连接操作的设计方式。

不过，这并不意味着 MongoDB 完全不需要关联字段或数据完整性检查。当前项目仍需要通过后端逻辑、索引和查询条件确保题目、问卷及答卷之间的关联正确。

### 3.3 AI 辅助检查题目校验与答案校验逻辑

**使用工具：** ChatGPT

**Prompt（整理后的代表性提示词）：**

> 请检查 Flask 问卷系统中的题目配置校验和答卷校验逻辑。系统支持单选题、多选题、文本题和数值题。请检查类型判断、必填规则、选项合法性、重复选项、选择数量、文本长度、数值范围和边界情况，并说明哪些校验应该在创建题目时完成，哪些应该在提交答案时再次完成。

**Result：**

AI 分析的重点包括：

- 题目标题和选项是否为空。
- 选择题选项是否重复。
- 答案是否属于当前题目的有效选项。
- 多选题是否重复选择，选择数量是否符合限制。
- 文本答案长度是否符合要求。
- 数值答案是否满足最小值、最大值和整数要求。
- 非法类型和不合理的校验规则是否会被接受。

当前项目将两类校验分别放在不同函数中：

- `validate_question_data(data)`：位于 `app/routes/questions.py`，负责检查问卷创建者提交的题目配置。
- `answer_is_valid(question, answer)`：位于 `app/routes/responses.py`，负责检查答卷者提交的答案。

这种划分使题目配置校验与答案提交校验各自承担明确的职责。

**代码分析示例：数值答案检查**

为了说明为什么数值校验不能只依赖简单的类型判断，构造了一个示例性初稿：

```python
# 示例性初稿：仅用于解释问题
def is_number(value):
    return isinstance(value, (int, float))
```

这段示例代码只检查类型，存在潜在问题：Python 中的布尔值也属于整数类型体系的一部分；此外，NaN 和无穷大等值也可能通过单纯的类型检查。

当前项目 `app/routes/responses.py` 中的实现为：

```python
def is_number(value):
    """只接受有限的数字，不接受布尔值。"""
    return (
        isinstance(value, (int, float))
        and not isinstance(value, bool)
        and math.isfinite(value)
    )
```

当前实现不仅判断数字类型，还明确排除布尔值，并通过 `math.isfinite(value)` 检查数字是否有限。

**是否修改：**

有修改。AI 对数值校验逻辑的分析用于辅助检查代码的完整性。我结合问卷系统对数字题答案的校验需求，对数值判断需要考虑的情况进行了梳理，并在文档中对比了简单类型判断与当前项目实际采用的判断方式。

**修改内容：**

1. **补充数值判断的边界情况。** 简单地判断一个值是否属于 `int` 或 `float` 类型还不够，因为 Python 中的布尔值也属于整数类型体系的一部分。如果不单独排除布尔值，`True` 和 `False` 也可能被误认为合法数字。

2. **记录当前项目的实际实现。** 在 `app/routes/responses.py` 中，`is_number` 函数不仅检查数值类型，还明确排除布尔值，并使用 `math.isfinite(value)` 排除 `NaN` 和正负无穷等非有限数值。核心代码如下：

   ```python
   def is_number(value):
       return (
           isinstance(value, (int, float))
           and not isinstance(value, bool)
           and math.isfinite(value)
       )
   ```

3. **说明该逻辑的实际作用。** 通过上述检查，数字题答案在进入后续的最小值、最大值和整数要求等校验之前，可以先排除类型不正确或数值异常的输入，从而提高答案校验的可靠性。

**我的思考与取舍：**

我认为前端输入控件只能改善用户体验，不能替代后端验证。客户端请求可以被直接构造，如果服务器不重新验证答案类型、选项 ID 和题目规则，就可能保存不符合问卷要求的数据。

因此，题目创建时需要检查规则本身是否合理，用户提交时还需要根据题目规则检查实际答案。这两层校验解决的是不同问题，不能简单地只保留其中一层。

### 3.4 AI 辅助分析条件跳转设计

**使用工具：** ChatGPT

**Prompt（整理后的代表性提示词）：**

> 请检查问卷系统的条件跳转设计。系统支持单选题、多选题和数值题触发跳转。请说明如何根据用户答案计算实际需要作答的题目，如何避免跳转回前面的题目，以及如何防止客户端提交已经被跳过的题目的答案。请结合 Python 代码解释关键逻辑。

**Result：**

当前项目将条件跳转拆分为两个主要函数：

- `jump_rule_matches(question, answer, rule)`：判断某个答案是否触发一条跳转规则。
- `get_active_question_ids(questions, received_answers)`：按照题目顺序计算本次答卷中实际应该作答的题目 ID。

单选题通过比较答案和规则中的选项 ID 判断是否跳转；多选题通过检查指定选项是否存在于答案数组中判断；数值题则支持相等、不相等、大于、大于等于、小于和小于等于等比较操作。

当前代码还会检查跳转目标的位置：

```python
candidate_index = position_by_id[target_id]

# 只允许跳转到当前题之后的题目。
if candidate_index <= index:
    continue

target_index = candidate_index
break
```

这里的判断要求目标题目位于当前题目之后，避免跳转回前面的题目。

在答卷提交过程中，后端会重新计算有效答题路径，并检查用户提交的答案是否包含按跳转规则应该被跳过的题目。如果包含，接口会拒绝此次提交。

**是否修改：**

有修改。AI 对条件跳转逻辑的分析用于辅助理解跳转规则的判断方式和服务端校验要求。我结合项目实际代码，对跳转条件的匹配、有效答题路径的计算，以及提交答案时的合法性检查进行了梳理，并在文档中补充了相应的实现说明。

**修改内容：**

1. **梳理不同题型的跳转判断。** 在 `app/routes/responses.py` 中，通过 `jump_rule_matches` 函数判断当前答案是否满足跳转条件。单选题根据选中的选项 ID 进行匹配，多选题检查指定选项是否包含在答案中，数字题则根据配置的运算符比较答案与规则值，例如大于、小于或等于。这样可以根据不同题型采用相应的判断方式，而不是对所有题型使用同一种规则。

2. **明确有效答题路径的计算方式。** 项目通过 `get_active_question_ids` 函数按照题目顺序遍历问卷，根据当前答案判断是否跳转到后续题目。如果符合跳转规则，就按照规则指定的目标继续处理；如果没有规则匹配，则继续按原有顺序答题。同时，代码会检查跳转目标的位置，避免跳转到当前题目之前的题目。

3. **补充服务端提交校验。** 在用户提交答卷时，后端会重新计算本次作答对应的有效题目列表，并检查提交的答案是否属于这条答题路径。如果答案对应的是已经被跳过的题目，系统会拒绝该次提交。这样可以避免仅依靠前端隐藏题目来保证跳转正确性，因为前端显示状态并不能代替服务端的业务校验。

4. **结合测试验证实际效果。** 在 `tests/test_api.py` 中，`test_single_choice_jump_skips_intermediate_question` 用于验证单选题条件跳转场景，检查满足跳转条件后，中间题目会被跳过。测试结果显示，该测试通过；项目现有的 9 项自动化测试也全部通过。

**我的设计考虑：**

我认为条件跳转不应该通过针对某个问卷的硬编码判断来实现，而应该使用题目中配置的 `jump_rules` 描述触发条件和目标题目。这样不同问卷可以设置不同的跳转逻辑，业务规则也更容易理解和维护。

同时，跳转目标应该受到顺序限制，后端也必须根据答案重新计算有效题目。否则，即使前端已经隐藏某道题，用户仍可能直接构造请求提交该题的答案。

需要注意的是，目前自动化测试中有一项测试验证了单选题跳过中间题目的行为。该结果不能单独证明多选题和数值题跳转的所有情况都已通过测试，后续仍可以补充对应测试用例。

### 6.1 完善题目配置与输入校验的设计

在题目管理部分，我重点梳理了不同题型对应的输入要求。不同类型的题目具有不同的数据结构和校验规则，如果只检查题目标题是否为空，而不检查选项和校验参数，就可能在问卷发布或用户答题时出现数据不一致的问题。

结合当前 `app/routes/questions.py` 中的 `validate_question_data` 函数，项目对以下内容进行了改进：

1. **题目基本信息：** 检查题目标题是否为空、去除首尾空白后的标题是否有效，以及标题长度是否超过限制。
2. **选择题选项：** 对单选题和多选题检查选项数量、选项内容及重复选项，避免出现选项不足、空选项或重复选项等情况。
3. **多选题限制：** 检查最少选择数量、最多选择数量和指定选择数量之间的关系，避免配置之间相互矛盾。
4. **文本题限制：** 检查最小长度和最大长度等参数，确保配置符合预期。
5. **数字题限制：** 检查最小值、最大值以及是否要求整数等配置，并验证相关参数之间的关系。
6. **条件跳转配置：** 检查跳转目标标识是否有效，并根据题型验证跳转条件是否符合对应规则。

这些检查改进使题目配置不再只是简单地保存用户提交的数据，而是先验证配置是否合理，再执行相应的数据操作。通过梳理这部分逻辑，我认识到，输入校验不仅关系到接口安全，也会直接影响后续问卷展示、答题和统计功能的可靠性。

### 6.2 加强答卷提交阶段的答案校验

题目配置阶段的校验和答卷提交阶段的校验并不相同。前者主要检查问卷创建者配置的题目是否合理，后者则需要检查填写者提交的答案是否符合题目要求。因此，不能认为题目创建时通过校验，后续提交的答案就一定合法。

结合当前 `app/routes/responses.py` 中的 `answer_is_valid` 函数，项目根据题目类型对答案进行验证，主要包括：

- **单选题：** 检查答案是否属于该题目定义的选项。
- **多选题：** 检查答案结构、选项合法性、重复选项以及最少和最多选择数量等限制。
- **文本题：** 检查答案类型、必答要求和文本长度限制。
- **数字题：** 检查答案是否为合法数值，并验证最小值、最大值和整数要求。
- **必答题：** 检查答案是否为空，避免必填内容缺失。

此外，提交接口还会检查答案对应的题目是否属于当前问卷、同一道题是否被重复提交，以及请求中是否包含必要的答案字段。

通过对这些规则进行梳理，我进一步明确了前端输入限制和后端数据校验的区别：前端可以帮助用户减少错误，但服务端仍然需要独立检查提交的数据，不能完全依赖页面控件来保证数据正确。

### 6.3 检查数值判断的边界情况

在数字题的校验中，仅判断数据是否属于 `int` 或 `float` 类型还不够。Python 中布尔值与整数类型存在继承关系，如果不单独排除布尔值，`True` 和 `False` 也可能被误认为合法数字。此外，`NaN` 和正负无穷等非有限数值也不适合作为普通数字题答案参与范围比较。

当前 `app/routes/responses.py` 中的 `is_number` 函数采用了更严格的判断方式：

```python
def is_number(value):
    return (
        isinstance(value, (int, float))
        and not isinstance(value, bool)
        and math.isfinite(value)
    )
```

其中，`isinstance(value, (int, float))` 用于检查数值类型，`not isinstance(value, bool)` 用于排除布尔值，`math.isfinite(value)` 则用于排除非有限数值。

这一实现使数字题的答案校验能够先排除不符合基本要求的数据，再进行数值范围和整数要求等检查。通过分析这段逻辑，我认识到，边界情况虽然不一定出现在普通答题流程中，但如果忽略它们，就可能使输入校验出现漏洞。

需要注意的是，当前 `app/routes/questions.py` 中也存在一个 `is_number` 函数，其检查逻辑与答卷提交模块并不完全相同。因此，后续可以考虑统一两个模块的数值判断规则，避免题目配置和答案提交对特殊数值采用不同标准。

### 6.4 检查条件跳转与有效答题路径

条件跳转是本项目中较重要的一项业务逻辑。它不仅影响用户填写问卷时看到哪些题目，还会影响哪些答案可以被接受。

当前项目通过 `jump_rule_matches` 函数判断答案是否满足跳转条件，并通过 `get_active_question_ids` 函数计算实际需要填写的题目路径。系统根据题目顺序处理跳转规则，对单选题、多选题和数字题采用相应的条件匹配方式；如果没有规则匹配，则继续按照原有顺序处理后续题目。

在跳转目标检查方面，当前实现会判断目标题目是否位于当前题目之后，避免跳转回前面的题目。提交答卷时，服务端还会重新计算有效答题路径，并拒绝包含已跳过题目答案的提交。

这种处理方式的意义在于，不能只通过前端隐藏题目来保证条件跳转正确。如果服务端不重新验证，用户仍可能通过直接构造请求提交不符合答题路径的答案。

项目中的 `tests/test_api.py` 包含 `test_single_choice_jump_skips_intermediate_question` 测试，用于验证单选题条件跳转并跳过中间题目的场景，该测试已通过。

通过检查这一模块，我认识到，条件跳转应当同时包含规则配置检查、答题路径计算和提交阶段验证，而不是单独实现一个控制页面显示的功能。

### 6.5 梳理 MongoDB 集合设计与索引配置

数据库部分是本项目的重要设计内容。结合当前 `app/init_db.py` 中的集合和索引初始化代码，我对各集合的职责及索引的实际用途进行了梳理。

项目使用四个主要集合：

- `users`：保存用户信息。
- `surveys`：保存问卷基本信息。

在索引方面，当前代码包含以下配置：

5. `submission_key` 稀疏唯一索引，用于对包含该字段的文档实施唯一性约束。

## 七、自己设计思路和内容

在本项目中，我不仅需要实现问卷创建、题目管理、答卷提交和统计查询等功能，还需要考虑数据应该如何组织、不同模块之间如何配合，以及怎样保证用户提交的数据符合业务规则。

在设计过程中，我主要围绕数据组织方式、题目配置结构、校验逻辑划分、条件跳转处理和数据库索引五个方面进行考虑。这些设计既要满足当前系统的功能需求，也要兼顾代码的可维护性和后续扩展能力。

### 7.1 四集合的数据组织方式

在设计数据库结构时，我首先考虑的是：是否应该将用户、问卷、题目和答卷全部放在同一个集合中。

如果采用单集合方案，虽然表面上可以减少集合数量，但不同类型的数据会混杂在一起。用户信息、问卷配置和答卷记录具有不同的字段结构，查询时也有不同的目的。如果将它们全部放入同一个集合，不仅会增加文档结构的复杂程度，还可能导致部分字段只对某类数据有意义，给后续维护带来困难。

因此，本项目采用四个主要集合分别保存不同类型的数据：

- `users`：保存用户信息及登录相关数据。
- `surveys`：保存问卷标题、创建者、发布状态、分享码等问卷基本信息。
- `questions`：保存题目内容、题型、选项、校验配置及条件跳转规则。
- `responses`：保存提交的答案、问卷标识、作答用户标识和提交时间等信息。

集合之间通过业务标识建立关联。例如，题目使用 `survey_id` 指向所属问卷，答卷也使用 `survey_id` 关联对应问卷。需要查询某份问卷的题目或答卷时，后端可以根据问卷标识查询相关集合中的数据。

我选择这种结构，是因为四类数据具有不同的生命周期和访问需求：用户信息不应随着某份问卷的修改而重复保存，题目需要独立增删和排序，答卷则需要按照问卷进行查询和统计。将它们分别存储，可以使数据职责更明确，也方便后续对各类数据建立适合的索引。

### 7.2 题目文档中嵌入配置数据

在题目集合的内部结构设计中，我进一步考虑了选项、答案校验规则和条件跳转规则应该单独存储，还是直接放在题目文档中。

如果把每个选项、每条校验规则和每条跳转规则都设计为独立文档，虽然可以分别管理，但读取一道题目时可能还需要查询多个集合，再将相关数据组合起来。对于本项目而言，这些配置通常依附于某一道题目，并且经常需要与题目内容一起读取，因此没有必要全部拆分成独立集合。

最终采用的思路是：题目本身保存在 `questions` 集合中，与题目紧密相关的配置则作为题目文档内部的字段保存。例如，选择题的选项可以放在 `options` 中，多选题限制可以放在 `validation` 中，条件跳转规则可以放在 `jump_rules` 中。

这种设计有三个主要考虑：

1. **减少读取时的额外查询。** 获取一道题目时，可以同时获得其选项和相关规则。
2. **保持题目配置的完整性。** 题目内容与其校验规则、跳转规则集中在同一文档中，更容易理解和维护。
3. **保留 MongoDB 文档结构的灵活性。** 不同题型可以根据需要保存不同的配置字段，不必要求所有题目都具有完全相同的结构。

当然，嵌入式设计并不意味着所有数据都应该嵌入。如果未来需要对选项或跳转规则进行大量独立查询、跨题目复用，或者这些配置的规模显著增长，就需要重新评估是否拆分。因此，本项目的设计重点不是一味追求嵌入，而是根据数据之间的依赖关系和实际访问方式进行选择。

### 7.3 将题目配置校验与答案校验分开

在设计后端校验逻辑时，我考虑到，问卷创建者配置题目和填写者提交答案虽然都涉及数据验证，但它们检查的对象并不相同。

题目配置阶段需要检查题目本身是否合理，例如标题是否有效、选择题是否具有足够的选项、多选题的数量限制是否矛盾，以及跳转规则的目标和条件是否符合要求。

答卷提交阶段则需要检查用户的实际答案，例如单选题答案是否属于合法选项、多选题是否超过选择数量限制、文本长度是否符合要求，以及数字题答案是否满足范围和整数约束。

如果将这些检查全部放进一个大型函数中，就容易混淆不同阶段的职责，也会增加后续修改某一种题型规则时的复杂程度。因此，项目将两类校验分别实现：

- `validate_question_data()`：负责检查题目配置是否有效。
- `answer_is_valid()`：负责检查用户答案是否符合题目要求。

这种划分使校验逻辑与业务阶段相对应，也便于分别测试题目创建和答卷提交过程。例如，即使一道数字题的配置合法，用户提交的答案仍然可能超出数值范围，因此提交阶段仍需要重新验证。

通过这种设计，我认识到，数据校验不应该只集中在某一个入口，而应该根据数据所处的业务阶段设置对应的检查规则。

### 7.4 由后端统一计算条件跳转路径

条件跳转会改变填写者实际需要回答的题目，因此我在设计这部分逻辑时，重点考虑了两个问题：如何判断跳转条件是否满足，以及如何保证提交的答案与实际答题路径一致。

在规则判断方面，项目通过 `jump_rule_matches()` 判断当前答案是否满足跳转规则，并通过 `get_active_question_ids()` 计算有效答题路径。不同题型采用不同的匹配方式，例如单选题根据选项标识匹配，多选题检查指定选项是否包含在答案中，数字题则根据配置的运算符进行比较。

在答题路径方面，系统按照题目顺序处理跳转规则，并检查目标题目的位置，避免跳转到当前题目之前的题目。如果没有符合条件的跳转规则，则继续按照原有顺序处理。

我选择由后端负责计算有效答题路径，而不是完全依赖前端隐藏或显示题目，是因为前端页面只能控制正常操作下的显示效果，不能保证提交请求一定符合页面状态。用户仍可能通过构造请求提交已经跳过的题目答案，因此服务端需要重新计算答题路径，并检查提交内容是否合法。

这种设计将条件跳转从单纯的页面交互提升为服务端也会执行的业务规则，使跳转判断与答案校验能够保持一致。不过，目前的测试主要验证了单选题跳过中间题目的场景，其他复杂跳转组合仍可以进一步补充测试。

### 7.5 使用索引配合数据约束与常见查询

在数据库设计中，我还考虑了索引应该服务于哪些业务需求。索引不仅影响查询效率，也可以在适当的场景下帮助数据库实施唯一性约束，因此需要结合实际数据访问方式进行选择。

本项目在 `app/init_db.py` 中配置了多种索引：

- 用户名唯一索引：避免用户名重复。
- 问卷分享码唯一索引：避免分享码发生冲突。
- `survey_id` 与 `order` 组合唯一索引：约束同一问卷中的题目顺序不能重复。
- `survey_id` 与 `submitted_at` 索引：支持按问卷查询答卷，并按照提交时间排序。

这些索引分别对应用户注册、问卷分享、题目排序和答卷查询等业务场景，而不是单纯为了增加索引数量。

同时，我也注意到，索引设计需要与实际写入逻辑配合。例如，当前代码定义了 `submission_key` 稀疏唯一索引，但答卷提交逻辑没有写入该字段，因此不能认为防重复提交功能已经实现。这个问题说明，索引存在并不代表业务约束已经生效，数据库设计还需要与后端写入流程一起检查。

通过这一部分设计，我认识到，索引应该根据实际查询和约束需求建立，并在开发过程中验证其是否真正发挥作用，而不是将所有字段都建立索引。

### 7.6 设计取舍与个人总结

综合以上设计，我认为本项目最重要的不是单独选择某一种技术，而是让数据库结构、后端逻辑和业务需求保持一致。

在数据组织方面，我将用户、问卷、题目和答卷分开存储，同时将与题目紧密相关的选项和规则嵌入题目文档，以兼顾职责划分与读取便利性；在后端实现方面，我将题目配置校验与答案校验分开，并由服务端统一计算条件跳转路径；在数据库约束方面，则根据用户名唯一性、分享码唯一性、题目顺序和答卷查询需求配置索引。

这些选择也存在需要继续完善的地方。例如，题目配置与答案提交模块中的数值判断逻辑尚未完全统一，防重复提交机制也需要进一步设计和实现。对这些问题进行识别，有助于我区分当前版本已经具备的能力与未来可以改进的方向。

通过本项目，我对 MongoDB 的理解从单纯使用集合保存数据，进一步延伸到文档嵌入与集合拆分的取舍、索引约束与业务逻辑的配合，以及服务端校验在数据一致性中的作用。这些设计思路也为后续扩展更多题型、复杂跳转规则和统计功能提供了基础。

## 九、问题与后续改进方向

结合当前代码分析，后续可以从以下方向继续完善：

1. **防重复提交：** 明确业务规则，并让 `submission_key` 或其他去重机制与答卷写入流程配套。
2. **并发情况下的题目排序：** 当前创建题目时读取最大顺序值再插入，删除题目时分阶段重新编号。后续可进一步设计并发保护和失败恢复方式。
3. **补充条件跳转测试：** 对多选题、数值题、多条规则和非法目标等情况增加测试。
4. **补充边界测试：** 对必填项、长度上下限、数值边界和截止时间进行更细致的测试。
5. **继续检查数据一致性：** 结合实际查询和更新流程验证索引是否有效，以及数据之间的关联是否满足业务要求。
